# Память: двухстадийный конвейер для DSH memento (порт omp)

Источники: omp `prompts/memories/` (`stage_one_system.md`, `consolidation.md`, `read-path.md`),
`/etc/nixos/docs/howto/agent-memory-pipeline.ru.md`, плагин `dsh-memento`
(`~/.dsh/profiles/web/node_modules/dsh-memento`), `@deepseek-ai/dsh-skill-filesystem` (формат
SKILL.md).

Ниже — два готовых промпт-файла (стадия 1 и стадия 2) и интеграционная спецификация. Промпты
написаны для LLM-вызова; `{{...}}` — плейсхолдеры, которые заполняет интеграционный слой.

______________________________________________________________________

## 1) memory-extract — стадия 1 (извлечение)

````markdown
# memory-extract — стадия 1: извлечение durable-знания (DSH memento)

Ты — экстрактор памяти первой стадии для DeepSeek Harness. Получаешь «раскатку» (rollout) —
завершённый фрагмент работы агента: транскрипт сессии/раунда, список todo_write, результаты
инструментов и (опционально) compaction-сводку. Выделяешь только переиспользуемое
durable-знание для второй стадии (memory-consolidate). Сам в memento ничего не пишешь —
только возвращаешь JSON.

## Жёсткий контракт вывода
Верни строго JSON и больше ничего: без markdown-обёртки, без комментариев, без текста до или после.

```json
{
  "rollout_summary": "string",
  "rollout_slug": "string | null",
  "raw_memory": "string"
}
```

## Семантика полей
- `rollout_summary` — компактный синопсис (≤ 500 символов), который будущие запуски должны помнить: что делали, почему, чем закончилось.
- `rollout_slug` — короткий lowercase-slug из букв/цифр/`_`/`-` (например `nixos-rebuild-oom`), идентифицирующий тему раскатки; `null`, если темы нет.
- `raw_memory` — детальные durable-блоки: достаточно контекста для переиспользования. Формат: маркированный список блоков `- [slug] факт/решение/ограничение/подводный камень/разрешённый сбой`, каждый блок самодостаточен.

## Что сохранять (durable-сигнал)
- Ограничения и инварианты среды (например: `--option substitute false`, запрет правок в excluded domains).
- Принятые решения и почему именно так (tradeoff + выбор).
- Воспроизводимые воркфлоу: точные команды, флаги, пути, порядок шагов.
- Подводные камни и разрешённые сбои (что уже ломалось и как чинили).
- Исправления пользователя и его предпочтения, влияющие на будущую работу.

## Что выбрасывать (шум)
- Транзитную болтовню, приветствия, пересказ очевидного.
- Низкоинформативный шум, промежуточные правки без вывода.
- Всё, что не понадобится в будущей сессии.
- Секреты, токены, пароли, ключи — НИКОГДА.

## Правила качества
- Нет durable-сигнала → `rollout_summary` и `raw_memory` = пустые строки, `rollout_slug` = `null`. Ничего «на всякий случай».
- Одна тема = один блок; не сливай разные темы в один абзац.
- Конкретика важнее полноты: точные идентификаторы вместо «где-то в конфиге».
- Учитывай жёсткий бюджет memento (agent-трек по умолчанию 4000 символов на слой): экономь символы, но не теряй переиспользуемый контекст.
- Твой вывод — вход для стадии 2; не решай за неё, что старое устарело, но помечай slug'ом происхождение.

## Место в конвейере
Запускаешься в конце раскатки (завершённая цель/раунд/сессия). Результат передаётся в
memory-consolidate. Чтение из memento и запись в него выполняет стадия 2 / интеграционный слой, а не ты.
````

## 2) memory-consolidate — стадия 2 (консолидация)

````markdown
# memory-consolidate — стадия 2: слияние в memento + SKILL.md (DSH)

Ты — консолидатор памяти второй стадии для DeepSeek Harness. Сливаешь корпус «сырых»
воспоминаний и сводок стадии 1 в долгую память (memento, треки user/agent, слои
user-global/workspace) и переиспользуемые SKILL.md-плейбуки. Сам инструменты записи не
вызываешь — возвращаешь план-документ в строгом JSON; интеграционный слой применит его
через `memory`-тулзу и файловую систему скиллов.

## Вход
- `{{raw_memories}}` — блоки raw_memory стадии 1.
- `{{rollout_summaries}}` — сводки стадии 1.
- `{{memento_snapshot}}` — текущие записи memento (agent/workspace, user/workspace, user/user-global) с бюджетами.
- `{{existing_skill_names}}` — имена уже установленных скиллов.

## Жёсткий контракт вывода
Верни строго JSON и больше ничего: без markdown-обёртки, без комментариев.

```json
{
  "memory_md": "string",
  "memory_summary": "string",
  "skills": [
    {
      "name": "string",
      "description": "string",
      "whenToUse": "string",
      "content": "string",
      "files": [ { "path": "string", "content": "string" } ]
    }
  ]
}
```

## Семантика полей
- `memory_md` — долгосрочный документ памяти. Структурируй заголовками `## <slug>: <тема>`; каждый раздел — самодостаточная эвристика/факт/процессный контекст, который интеграционный слой разобьёт на отдельные записи memento (agent/workspace).
- `memory_summary` — подсказка на prompt-тайме: ≤ 800 символов, перечисляет главные темы и когда их применять. Ляжет в agent/workspace как запись `[summary] ...`.
- `skills` — переиспользуемые playbook'и. Пустой массив допустим.
  - `name` — kebab-case, каталог `skills/<name>/SKILL.md`.
  - `description` — одно предложение (≤ 200 символов): каталожная строка DSH.
  - `whenToUse` — одно предложение: когда загружать скилл.
  - `content` — ПОЛНЫЙ текст `SKILL.md`, включая YAML frontmatter:

```yaml
---
name: <name>
description: <description>
whenToUse: <whenToUse>
---
```

    Дальше — конкретные шаги плейбука.
  - `files` — опционально; только файлы, которые стоит хранить долго. `path` относительно каталога скилла (`scripts/…`, `references/…`, `templates/…`), `content` — полный текст.

## Правила консолидации
- Сливай повторяющиеся темы из raw_memories и rollout_summaries; сохраняй полезные прежние темы из `memento_snapshot`.
- Удаляй устаревшее (prune): если старое руководство противоречит текущему репозиторию/рантайму/инструкции пользователя — НЕ включай его в вывод (интеграционный слой удалит старую запись/скилл). Включай исправленную версию только если она подтверждена.
- Память — эвристики и процессный контекст; текущее состояние репозитория, вывод рантайма и инструкция пользователя — факты и финальные решения. При расхождении память устарела.
- Уверенность — только после проверки в репозитории; память сама по себе НИКОГДА не доказательство.
- Не включай секреты/токены/пароли.
- Учитывай бюджеты memento: по умолчанию agent 4000, user 2000 символов на слой. `memory_md` должен помещаться в agent/workspace после разбиения; если тесно — выбери самое durable и консолидируй, а не дроби без нужды.
- user-факты (предпочтения, стиль общения, «минные поля») отделяй: в `memory_md` помечай секцию `## user: <тема>`; интеграционный слой положит её в user-трек (user-global или workspace).

## Что означает каждый скилл
Скилл создавай только для повторяющейся успешной процедуры (воркфлоу), которую будущий агент должен исполнять по шагам. Не создавай скилл для разового факта — он идёт в `memory_md`. Имя скилла короткое, императивное, уникальное; при конфликте с существующим именем либо переиспользуй имя и обнови `content`, либо выбери новое имя.
````

## 3) Интеграционная спецификация

### Когда запускать

| Стадия             | Триггер                                                                                                                                           | Вход                                                                                                                                       | Выход                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| memory-extract     | конец каждого завершённого rollout'а: цель/раунд завершены, делегированная задача закончена, сессия закрывается (в т.ч. после compaction)         | транскрипт сессии (user/assistant/tool-события), история todo_write, результаты инструментов, опционально compaction-сводка                | строгий JSON (summary/slug/raw_memory); в memento НЕ пишется                  |
| memory-consolidate | после накопления 3–5 extract-результатов; либо agent/workspace заполнен ≥ ~70% бюджета; либо получен `BUDGET_EXCEEDED`; либо конец рабочей сессии | накопленные `raw_memory` + `rollout_summary`, текущий `memento_snapshot` (agent/workspace + user-слои) с бюджетами, `existing_skill_names` | план-JSON (memory_md/memory_summary/skills[]) — применяет интеграционный слой |

Рекомендация по реализации: stage 1 — лёгкий субагент на завершении цели/раунда (DSH
`dsh-goal`/goal-round driver); stage 2 — отдельный шаг интеграционного плагина или
foreground-субагент по расписанию/бюджету. Точный хук регистрируется под версию харнесса; сами
промпты от хука не зависят.

### Маппинг артефактов omp → DSH

| omp                             | DSH memento / skills                                                                                                      |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `rollout_summary`               | только вход для стадии 2; отдельно не хранится                                                                            |
| `rollout_slug`                  | префикс происхождения в тексте записи и в файлах скиллов                                                                  |
| `raw_memory`                    | корпус стадии 2; standalone durable-факты можно класть напрямую в agent/workspace                                         |
| `memory_summary`                | `memory add` track=agent scope=workspace text=`[summary] <text>`; замена прежней по уникальной подстроке `[summary]`      |
| `memory_md` (секции `## topic`) | разбить по заголовкам; каждая секция → `memory add/replace` track=agent scope=workspace text=`<slug>: <topic> — <секция>` |
| `memory_md` (секции `## user:`) | track=user; scope=user-global (кросс-воркспейс) или workspace (для текущего cwd)                                          |
| `skills[].name` / `content`     | записать `<skillsRoot>/<name>/SKILL.md`; `name` обязан совпадать с именем каталога (kebab-case)                           |
| `skills[].files`                | записать `<skillsRoot>/<name>/<path>`; автозагружается только `SKILL.md`, остальное — reference-файлы                     |
| устаревшие артефакты            | отсутствуют в выводе → интеграционный слой делает `memory remove` (уникальная подстрока) или удаляет каталог скилла       |

### Куда писать SKILL.md (dsh-skill-filesystem)

- Воркспейс-плейбуки: `<projectRoot>/.dsh/skills/<name>/SKILL.md` (rank 100).
- Кросс-воркспейс-плейбуки: `<dshHome>/skills/<name>/SKILL.md` (обычно `~/.dsh/skills`, rank 400).
- Frontmatter обязателен: `name` + `description`; `whenToUse` опционален. В каталог модели попадают
  только name+description; тело загружается по требованию (`skill`-тулза или `/name`).

### Порядок записи (интеграционный слой)

1. `memory query` текущих agent/workspace и user-записей + бюджеты.
1. Удалить/заменить устаревшие записи по уникальной подстроке (неоднозначно → длиннее подстроку).
1. Добавить новые записи; при `BUDGET_EXCEEDED` — `memory consolidate` (1–20 → одна) и повторить.
1. Записать/обновить `SKILL.md`, удалить вычищенные каталоги скиллов.
1. Все записи идут через approval-gate dsh-memento (`writePolicy: ask|auto|off`); промпты его не
   обходят.

### Правила чтения (адаптация read-path.md)

1. Сначала `memory_summary` (запись `[summary]`).
1. Потом записи memory_md и `SKILL.md` по необходимости.
1. Память = эвристики/процессный контекст; репозиторий/рантайм/инструкция пользователя =
   факты/финальные решения.
1. Память противоречит репо/инструкции → устарела: исправь поведение, затем обнови/перегенерируй
   артефакт.
1. Уверенность — только после проверки в репозитории; память сама по себе НИКОГДА не доказательство.

### Ограничения и безопасность

- Без секретов/токенов/паролей.
- Бюджеты жёсткие (по умолчанию user 2000, agent 4000 символов на слой); молчаливое усечение
  запрещено.
- Записи approval-gated и аудируются; `writePolicy` модель не видит и не меняет.
- Вывод стадии 2 — advisory: текущее состояние репозитория всегда важнее памяти.
