# Independent verification of the patch series

One verifier per patch, each in its own worktree at the base commit (`/tmp/up/v0N` = upstream
`e0c1f6d` + the vendored path dependencies, because `git.lilithsemi.com` does not answer this
machine). Every verifier was asked to *falsify* its patch, not to confirm it, and to report the
verdict, the evidence and what it could not check.

| 04-git-worktree-root    | **broken → fixed, re-verified (holds)** | Non-vacuous red/green: with only the `flake_ref.zig` hunk reverted, both tests fail (lines 627/732). On a real repository (tracked files, an untracked 200 MiB sparse blob, a gitignored file) `fix instantiate` records `refType="git"`, `url="file://…"` and a snapshot of the tracked files only — the 200 MiB blob never reaches the store and `StreamTooLong` does not appear — while plain `eval` still reads the directory in place (`parseFlakeRef` → `path`, untracked visible). Regression found: a work-tree root with an **unborn HEAD** (`git init`, nothing committed) has no revision to fetch, so the new git resolution failed with `FetchGitRevisionNotFound` where the old directory copy worked. Fixed in v3: `hasResolvedHead` keeps such a tree on the `path` route, with a regression test; `zig build test-expr` → 543 passed / 0 failed. The verifier's second round showed the policy was still too permissive: an *empty*, *garbage* or *missing* HEAD, an empty symbolic ref, and a `.git` **symlink** to an unborn checkout all still took the git route and failed with `FetchGitRevisionNotFound` (the same class of failure). Fixed in v5: only a HEAD that proves resolvable goes to git — a symbolic ref that exists loose or in `packed-refs`, or a full 40-hex detached id; every other shape (unborn, empty, garbage, missing, unreadable, symlinked) keeps the directory copy, `.git` as a *file* (linked work tree, submodule) stays on the git path as before, and a `.git` symlink is read through so a symlinked unborn checkout is caught. A table test covers all of those shapes; `zig build test-expr` → 543 passed / 0 failed. The third round confirmed it: with the verifier's own four tests the suite holds 552 cases — 547 passed, 5 skipped, 0 failed (`/tmp/up/v04d-test-expr-final.log`), and the same tree without the `flake_ref.zig` hunk fails (15/17 steps, the discriminating tests red), every broken HEAD shape (`: > .git/HEAD`, `garbage-not-a-rev`, missing HEAD, `ref: ` with an empty ref) returns `path` and `fix instantiate` succeeds on such a directory (no `FetchGitRevisionNotFound`), a `.git` symlink to an unborn checkout answers `path` while one to a committed repository answers `git`, the green paths are intact (packed-refs-only and detached HEADs → `git` with `names="p.txt"`/`"d.txt"`, `.git`-as-a-file → `git` and `FetchGitFailed` on a broken gitdir like Nix's flake layer, a committed repository → only tracked files in the store, `fix eval` → `path` with untracked visible), and the negative control still fails the discriminating tests. Not checked: end-to-end `build`/`switch`/`run`/`shell` (same `enableStoreWrites` gate, only `instantiate` was driven), `--flake <path>` installs and the lock/narHash flows. |
