# Port status: QuickShell → pleamar

What of the legacy shell in `files/quickshell` has a counterpart in this port, and what has not.
Written because "the capsules are glass" was asked for twice and delivered late: a list makes the
gaps visible before they are asked about again.

**How this was made.** The inventory is the QML tree itself (`Bar/Modules`, `Components`,
`Services`, the top-level areas, and the two big trees `Chaldea/` and `greeter/`). A counterpart is
a scene (`shells/*`), a plugin (`lib/plugins/*`) or a library
(`lib/{capsule,icons,menu,palette}.plm`); evidence is the file headers that name their legacy
(`// Legacy: …`), `docs/INTERFACES.md`, and the behaviour itself. Statuses are by behaviour, not by
line: "ported" means the thing works in the port, not that its QML was translated one-to-one.

**Legend**

|             |                                                                                                                                                           |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **ported**  | a counterpart exists and its behaviour is there                                                                                                           |
| **partial** | a counterpart exists with a known gap (named in the note)                                                                                                 |
| **absent**  | nothing in the port                                                                                                                                       |
| **engine**  | the QML object is plumbing the scene language replaces outright (a behaviour, a layout host, a texture helper); there is nothing to port object by object |

### The tray's menu, and where it comes from

**Settled 2026-10-26: the engine reads it, no plugin is needed.** `bar.luau` asks
`sys.ask("tray.menu", key)` when the right button lands on an icon, and the engine answers the
item's own `com.canonical.dbusmenu` tree — `get tm.count` was 8 for vicinae («Toggle Vicinae»,
«Vicinae v0.29.0 [unknown]», a separator, «About Vicinae», «Settings…», …) and for Steam its five
recent games, Shop and Library, drawn on the bar's `barmenu` surface (screenshot, 2026-10-26). When
the ask fails, the logic falls back to `tray.context`, the application's own menu.

The earlier plan here — a `lib/plugins/traymenu` running `busctl` and parsing the layout — was
written for 0.4.11, where the record's `menu` arrived empty. The evidence it rested on still holds
and is worth keeping, because it is what the engine has to cope with: an item's menu is
`com.canonical.dbusmenu` at the path its `Menu` property names, the signature differs by
implementation (Steam takes `iias` with the old `parentId` as `i`, the spec's newer form is `uias`;
vicinae answered "No such method `GetLayout`" at its `/MenuBar` on 2026-10-24), and activation is
`com.canonical.dbusmenu.Event(id, "clicked", …)`.

What is left is depth and room: the tree arrives flat, and the menu draws at most 8 rows in its
300×176 surface.

## The short version

Ported, in the sense that the thing works: the bar and all its capsules, the launcher, notifications
(cards), overlay, overview, the drawer pages, the plugins (cover, meta, mpd, pill, spectrum,
genelec), the palette and its scripts, and the login/lock card.

Absent outright: the tray menu's submenu search field (`SubmenuHost`, `MenuUtils`), the number-roll
animations, and Chaldea's 340 art files.

Partial, with the gap named above: the tray's hold/collapse state machine, connectivity/VPN, weather
values (no network on this host), notifications history, the greeter's theme variants, and the
helper set.

### The order the gaps fight each other in

1. The lock screen's own cost, at its own size. The preview says so itself:
   `this scene does not keep up: 8.6 ms a frame against the 4.2 the screen gives` at 1280x720, and
   the lock is a fullscreen glass card on a 4K monitor. A lock that stutters is the first thing a
   session shows; measure `pleamar --report lock` on the real size before the login path is trusted
   with it.
1. The tray's depth: the engine hands `children` over and `open_tray_menu` drops them. Nothing on
   this host nests, so it waits for an application that does.
1. Two plugin tails that cost one approval round to close (below).
1. Everything else in the tables above, with the settings surface folded into whichever widget is
   being ported.

### The lock as the engine runs it (measured 2026-10-27)

What stopped the lock was the engine, in two ways. The first is patched here; the second is open.

- **The engage was asked for before there was anything to ask with.** `src/render.rs:3526` engages
  the lock from the render loop once the surface's `open:` is true, and
  `src/platform/wayland.rs:893-897` skips lock surfaces while placing, on purpose — so a scene whose
  only surface is the lock leaves `placed` empty, and the `none of the monitors asked for …` warning
  that follows is about placement, not monitors. The render thread starts before the platform has
  made `LOCKS`, its one request was dropped silently and remembered as sent, and the loop then went
  to rest with the session unlocked: `WAYLAND_DEBUG=1` showed the manager bound and `lock` never
  sent. **Fixed** by `packages/overlays/pleamar-lock-engage.patch` — the request is remembered only
  once the platform took it, a refused one is asked again, and the platform sends
  `ToRender::Repaint` when it can take it. Verified on the live session:
  `lock · the session is locked`, `lock.held` reads 1, and the engine hands 3840×2160 frames to the
  compositor.
- **A lock the compositor ends crashes the scene.** When `lock.held` goes back to 0 the engine sends
  `unlock` on the object the compositor already took away —
  `wl_display#1: error 0: invalid object 31`, `Io error: Invalid argument (os error 22)` — and the
  scene exits. Hyprland then answers the next locker with
  `lock · the compositor did not grant the lock, or ended it`, so one session gets exactly one lock.
  Open: the release path has to drop its own bookkeeping when `finished` arrives instead of
  unlocking a proxy that is gone.
- **`describe` cannot see it.** `pleamar --say lock describe` answers `nothing on screen`, which is
  the protocol working: a `kind: lock` surface and `agent: hidden` are never told. A lock scene with
  no surface at all looks exactly as healthy from outside.
- **The password has a stack now.** `security.pam.services.pleamar` (fprintd `sufficient`, then
  `pam_unix`) writes `/etc/pam.d/pleamar`, which is the name the engine asks for; it lands with the
  next switch. No fingerprint reader is plugged in, so the finger half falls through every time.
- **The frame cost is still unmeasured.** The one good engage lasted seconds, and the `--report` run
  arrived after the compositor had stopped granting locks. 3840×2160 gets numbers next time; nothing
  so far suggests the preview's 8.6 ms — this is one glass card, not a wall of widgets.
